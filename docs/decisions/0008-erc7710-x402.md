# ADR 0008: Paying x402 sellers that accept ERC-7710 delegations

Status: proposed, deferred (2026-11-25). Revisit when sellers outside MetaMask's own examples use it.

## Context

cyphos-guard pays x402 through the per-grant `X402Vault`. The seller asks for an EIP-3009 `TransferWithAuthorization`;
a delegation can't produce that signature, so the vault signs it through ERC-1271 and enforces the seller list and the
per-payment cap on-chain. That works with any standard x402 seller and facilitator. The cost is money parked in a
vault between top-up and settlement, which is where issue #2 and vault review findings 9 and 10 came from.

MetaMask now offers a second way to pay x402 (Smart Accounts Kit 1.6.0+, `@metamask/x402`, checked 2026-11-25):

- The seller offers `scheme: "exact"` with `extra: { assetTransferMethod: "erc7710" }`.
- The buyer sends `{ delegationManager, permissionContext, delegator }` instead of a USDC signature. The
  facilitator redeems the delegation chain during settlement.
- `createx402DelegationProvider` (in `@metamask/smart-accounts-kit/experimental`) builds an open delegation and adds
  redeemer, allowed-targets, timestamp and payee caveats.
- The only facilitators named are MetaMask's own (Base, Base Sepolia, Monad).

Docs: https://docs.metamask.io/smart-accounts-kit/guides/x402/overview/ and
https://docs.metamask.io/smart-accounts-kit/development/reference/x402/

Today cyphos-guard rejects these offers: there is no EIP-3009 route to pay them.

## Proposal

When an offer uses `erc7710`, the agent redelegates from its existing grant instead of using the vault:

```
owner account ──grant (owner's caveats)──▶ agent ──narrow redelegation──▶ facilitator ──redeem──▶ USDC.transfer(payTo, amount)
```

The narrow redelegation is signed by the agent key and pins redeemer = the facilitator addresses from the offer,
target = the USDC contract, one `transfer` to `payTo` for exactly `amount`, `LimitedCalls(1)` and a few minutes'
expiry. The DelegationManager checks every link at redemption, so the owner's caveats still apply: period budget,
`ERC20PerTransferCapEnforcer`, allowed recipients.

Changes:

- SDK `fetchPaid`: recognise `erc7710` offers, build and sign the redelegation, encode the payload. Prefer the vault
  path when a seller offers both, until this has run in production for a while.
- Compiler: an `x402` permission's seller list becomes the allowed USDC recipients on the grant, so a seller that isn't
  listed can't be paid on this path either.
- Revoke needs nothing new: `disableDelegation` on the grant breaks every chain built on it.

## Open questions (to settle with fork tests before building)

1. **Co-signer and over-limit approval.** The `CosignerEnforcer` reads its signature from caveat `args`, and the
   cosignature binds the redeemer. Here the facilitator redeems, so the cosignature would have to bind the facilitator
   and travel inside `permissionContext`. Args aren't covered by the delegation hash (ADR 0005), so this may work, but
   it depends on the facilitator passing `permissionContext` through unchanged. Owner approvals (ADR 0004) would need
   the one-shot delegation redelegated to the facilitator the same way. Until this is proven, `erc7710` offers above
   the routine limit are refused rather than escalated.
2. **Facilitator verification.** MetaMask's facilitator simulates the chain before settling. Check that it accepts a
   chain whose root is a Hybrid DeleGator and whose caveats include our two enforcers.
3. **Gas.** The facilitator pays gas for a longer chain; check that it doesn't refuse it.

## Consequences

- For these sellers: no vault and no parked balance; x402 spend counts against the same budget as normal payments.
- A second payment path to test and document. The red-team catalog needs the same attacks on this path, e.g. a
  redelegation to another redeemer, a different payee, a replayed payload.
- Depends on an API MetaMask marks experimental and on a facilitator we don't run.
- Not built yet: few sellers use this method, and the vault already covers standard x402 sellers.
